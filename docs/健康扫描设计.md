# 健康扫描功能

> ✅ 已实现。批量验证邮箱池内账号的 token 有效性，标注状态，页面展示。
> 参考：reg-factory 号池扫描（低频串行 + 风控自动暂停）、OutlookManager 账户活性检测。

---

## 一、目标

解决"导入账号后不知道哪些能用"的问题：
- 37 个 outlook 账号 token 全部 `invalid_grant`，需要批量检测确认
- 后续导入新账号时自动验证，不健康的标注 dead
- 页面直观展示：正常 / 异常 / 未检测 / 已失效

---

## 二、状态模型

`EmailAccount.status` 现有 3 种：`available` / `using` / `dead`

扩展为 5 种（新增 `healthy` / `unhealthy`）：

| status | 含义 | 能否取号 |
|---|---|---|
| `available` | 未检测，默认状态 | ✅ 可以 |
| `healthy` | 最近检测通过，token 有效 | ✅ 可以 |
| `using` | 占用中 | ❌ |
| `unhealthy` | 检测失败（token 过期/被风控），但账号可能还活着 | ❌ |
| `dead` | 彻底失效（账号被封/永久无法恢复） | ❌ |

> claim 逻辑修改：只 claim `available` 和 `healthy` 状态的号。

## 三、检测逻辑

### 检测方式：Graph API 静默拉取

```python
# 伪代码：对池内每个 outlook 账号执行
def check_one(account: EmailAccount) -> tuple[str, str]:
    """返回 (new_status, detail)"""
    cred = json.loads(account.account_json)
    refresh_token = cred.get("refresh_token", "")
    client_id = cred.get("client_id", "")

    if not refresh_token or not client_id:
        return "unhealthy", "缺少 client_id 或 refresh_token"

    try:
        # 尝试刷新 token（与 outlook.py _request_access_token 逻辑一致）
        token = _request_access_token(refresh_token, client_id, GRAPH_SCOPE)
        access_token = token["access_token"]

        # 用 access_token 调 Graph API 验证账号可用
        req = urllib.request.Request(
            f"{GRAPH_BASE}/me/messages?$top=1&$select=id",
            headers={"Authorization": f"Bearer {access_token}"},
        )
        urllib.request.urlopen(req, timeout=15)

        # 成功：更新 refresh_token（微软可能轮换 token）
        if token.get("refresh_token"):
            cred["refresh_token"] = token["refresh_token"]
            account.account_json = json.dumps(cred)

        return "healthy", "Graph API 验证通过"

    except urllib.error.HTTPError as e:
        code = e.code
        body = e.read().decode("utf-8", errors="replace")[:300]

        # 400 + invalid_grant = token 绑定的 client_id 不匹配 或 账号被风控
        if code == 400 and "invalid_grant" in body:
            # 进一步判断：用 IMAP scope 再试一次
            try:
                token = _request_access_token(refresh_token, client_id, IMAP_SCOPE)
                return "healthy", "IMAP scope 验证通过（Graph scope 缺失）"
            except:
                pass
            return "unhealthy", f"invalid_grant: token 失效或 client_id 不匹配"

        # 401/403 = 账号可能被锁
        if code in (401, 403):
            return "unhealthy", f"HTTP {code}: 账号可能被风控锁定"

        return "unhealthy", f"HTTP {code}: {body[:100]}"

    except Exception as e:
        return "unhealthy", f"异常: {e}"
```

### 检测策略：低频串行（参考 reg-factory）

```
规则：
1. 串行检测，不并发（避免触发微软批量请求风控）
2. 每个账号间隔 2-3 秒（随机抖动）
3. 连续 3 个账号返回风控响应（429/403）→ 自动暂停
4. 单次扫描上限 50 个（大批量分批跑）
5. 只检测 outlook provider 的账号
6. 7 天内检测过的跳过（除非手动强制）
```

## 八、风控防护

参考 reg-factory 的号池扫描策略：

```
1. 串行不并发（每号间隔 2-3s 随机）
2. 连续 3 个返回 429/403 → 自动暂停，标记 paused=true
3. 暂停后 30 分钟内不允许再次扫描
4. 单次最多 50 个（防长时间运行）
5. 检测只读：Graph API GET /me/messages（不发送/不修改邮件）
6. 7 天缓存：检测过的号 7 天内不重复检测（除非 force=true）
```

## 九、自动降级（fail_count）

`EmailAccount.fail_count` 字段记录连续失败次数，健康扫描与心跳保活共用同一套降级机制：

| 触发条件 | 动作 |
|---|---|
| 检测成功 | `fail_count = 0`，status 置 `healthy` |
| 检测失败，累计 ≥ 3 次 | 降级为 `unhealthy`（暂停取号，等待下次扫描恢复） |
| 检测失败，累计 ≥ 6 次 | 降级为 `dead`（彻底剔除，不再参与扫描和保活） |

阈值常量定义在 [pool_service.py](../app/services/pool_service.py)：

```python
FAIL_UNHEALTHY_THRESHOLD = 3   # 连续失败 3 次 → 降为 unhealthy
FAIL_DEAD_THRESHOLD = 6        # 连续失败 6 次 → 降为 dead
```

降级由 `_apply_check_result(acc, ok, detail)` 统一处理，健康扫描和心跳保活都调用该函数，避免逻辑分散。

## 十、client_id 维度统计

新增 `GET /api/admin/pool/client-id-stats` 接口与「邮箱池」页统计卡片，按 `client_id` 维度聚合号池健康分布：

```
GET /api/admin/pool/client-id-stats?provider=outlook

响应：
{
  "code": 0,
  "data": [
    {
      "client_id": "9e5f94bc...29d753",   // 脱敏：前8位...后4位
      "total": 30,
      "healthy": 28,
      "unhealthy": 2,
      "dead": 0,
      "available": 0,
      "using": 0,
      "healthy_rate": 93.3
    }
  ]
}
```

用途：识别被微软封禁的 client_id。若同一 client_id 下的号集体失效（healthy_rate < 30%），说明该 client_id 可能已被微软拉黑，需更换 client_id 并重新获取 token。详见 [docs/获取ClientID指南.md](获取ClientID指南.md)。
