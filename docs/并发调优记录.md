# Graph 通道并发调优记录（2026-11-22）

## 结论速览

```
单 client_id + 无代理的实测边界：
  聚合 10 rps（15 并发收码）= 100% 成功，收码 ~30s
  聚合 13 rps（20 并发收码）= 整体退化，收码 230s，成功率 60%
  微软限流方式 = 拖慢（请求 stall 15~30s），全程无 429
  单邮箱限流 = 持续 >1.3 rps/箱 也会被 stall（重试型场景注意）

现配置（默认值，均可 env 覆盖）：
  路由策略   **IMAP 优先**（约 70% 的号有 IMAP scope），
             无 IMAP scope（约 30%）直连 Graph 兜底
  Graph 桶   8 rps 起，AIMD 自适应 [3, 10]（无 scope 号排队用）
  token 桶   4 rps 起，AIMD 自适应 [2, 8]
  IMAP 车道  连接复用 + NOOP 保活，软上限 24 并发
  30 并发预期 IMAP ~21 + Graph ~9，收码 30~45s，成功率 ~100%
```

## 根因（旧代码为什么 20 并发就崩）

1. **聚合限流撞墙**：Graph 轮询全部从本机直连（不走账号代理），995 个号
   共用 Thunderbird 公共 client_id `9e5f94bc-…`。20 线程 ≈ 13 rps 聚合，
   撞微软「client_id + 出口 IP」限流线。
2. **限流被放大成雪崩**：旧代码收到任何 5xx 直接 `raise` → 该账号整条
   Graph 通道死亡 → 全批挤进 IMAP 降级 → IMAP 每轮还要重连（TLS+XOAUTH2
   握手 2~4s）→ 二次加压 → 集体 230s。60% 成功率的直接死因是代码。
3. **token 白刷**：每次收码都刷 refresh_token（access_token 明明能用 1h），
   批量开始时几十个刷新同时砸 login 端点。

## 改动清单

| 改动 | 位置 |
|---|---|
| client_id 级令牌桶 + AIMD 自适应（ok +0.5/20次，429 ×0.7，超时 ×0.9） | outlook.py `_TokenBucket` |
| 429/503 歇 Retry-After 继续轮询，绝不 raise；连续 3 整轮 5xx 才降级 IMAP | outlook.py `_graph_wait_code` |
| access_token 进程内缓存（提前 5min 过期，Graph/IMAP 双 scope 分开） | outlook.py `_cached_token` |
| 双车道路由：**IMAP 优先，无 IMAP scope 的号 Graph 兜底**（首次失败即记忆） | outlook.py `_wait_mail_sync` |
| IMAP 连接复用（每轮不再 TLS 重连）+ NOOP 保活 + 断线重连 | outlook.py `_imap_wait_code` |
| 取号基线抓取 / 健康扫描 / 保活 / 后台邮箱查看全部过令牌桶 | outlook.py + pool_service.py |

## 数据

### IMAP 单车道基准（.tmp_diag/imap_bench.py，30 号采样，21 号有 IMAP scope）

| 并发 | 轮次/worker/分 | p50 | p95 | max | 连接失败 | 错误 |
|---|---|---|---|---|---|---|
| 20 | 29.3（满速） | 612ms | 755ms | 848ms | 0 | 0 |
| 21 | 29.3（满速） | 607ms | 708ms | 1699ms | 0 | 0 |

- 21 并发满速运转、零错误、前后半程无衰减——**IMAP 车道天花板远高于实测值**，
  无 client_id 级聚合限流，约束只剩每 IP 连接数。
- **重要发现：约 30%（9/30）的号没有 IMAP scope**（原始授权只含 Graph），
  token 端点对 IMAP scope 直接拒绝。分流层已做记忆（`_imap_no_scope`），
  这些号车道满员时直接 Graph 排队，不送 IMAP 撞死。

### 实战（RegiForge 注册收码，每箱 ~0.7 rps）

| 并发 | 成功率 | 收码耗时 |
|---|---|---|
| 10 | 9/10 | 26~32s |
| 15 | 15/15 | ~30s |
| 20 | 12/20 | 229~236s |
| 25 | 16/25 | 238~251s |

### 基准（.tmp_diag/graph_bench.py，6 号轮打，读自己收件箱）

| 目标 rps | 实收 rps | p50 | p95 | max | 429 |
|---|---|---|---|---|---|
| 8 | 4.9 | 652ms | 15.6s | 15.8s | 0 |
| 12 | 1.2 | 749ms | 30.6s | 30.7s | 0 |
| 15 | 3.8 | 649ms | 15.7s | 17.3s | 0 |

注：基准单箱 1.3~2.5 rps，撞的是**单邮箱限流**（与聚合限流不同维度），
但「零 429、纯拖慢」的限流形态与实战一致。实收 rps 塌缩就是 230s 收码的机理。

## 可调参数（env）

| 变量 | 默认 | 说明 |
|---|---|---|
| MAILPOOL_GRAPH_RPS | 8 | Graph 桶初始速率（无 scope 号 / 兜底用） |
| MAILPOOL_GRAPH_RPS_MAX | 10 | AIMD 上限（实战标定，别乱调高） |
| MAILPOOL_GRAPH_RPS_MIN | 3 | AIMD 下限 |
| MAILPOOL_IMAP_MAX_CONNS | 24 | IMAP 车道软上限 |
| MAILPOOL_TOKEN_RPS / _MAX / _MIN | 4 / 8 / 2 | token 桶 |
