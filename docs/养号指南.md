# Outlook / Hotmail 邮箱养号指南

> 基于开源项目（OutlookRegister、OutlookManage、KiroX、outlook-helper、email-warmup-stack 等）与批量运营实践整理。
> 适用于：批量注册的邮箱、购入的令牌号（token）、长期接码号池的保活与降风险。
> 目标：让账号在微软风控（信任评分）下安全存活、正常收信，尽量不触发封禁/限制。

---

## 一、为什么新号必须养

微软对新注册账号有一套**信任评分（reputation / risk score）**体系，新号天然低分，处于高强度监控期。算法主要观察：

| 维度 | 风控关注点 |
|---|---|
| 登录频率 | 是否突然高频登录、多设备登录 |
| IP 地理位置 | 是否频繁跳区（同一账号在不同国家登录） |
| 邮件发送速度 | 是否注册后立即群发 |
| 重复操作模式 | 多个账号是否行为雷同（同操作、同时间、同 IP） |
| 邮件交互 | 是否阅读、回复、打开邮件 |
| 注册信息 | 用户名是否规律（test001、test002）、生日是否<18 岁 |

**结果分级**（从轻到重）：

1. **临时限制（temporary block）**——登录被拦截，验证后恢复
2. **service abuse mode**——服务滥用模式，功能受限
3. **强制验证**——要求手机号 / 辅助邮箱验证
4. **永久封禁**——不可恢复

## 二、养号核心原则（四条铁律）

1. **IP 稳定**：一个账号固定一个 IP / 一个地区，绝不跳区。这是第一红线。
2. **环境隔离**：一账号一环境（指纹浏览器 / 独立浏览器 profile），杜绝硬件指纹关联。
3. **信息隔离**：严禁多账号共用密码、辅助邮箱、手机号——否则"连锁封禁"。
4. **渐进式使用**：先模拟真人（阅读、订阅、互发），再逐步加大负载，绝不一上来就跑量。

## 三、分阶段养号计划

### 阶段 0：注册期（当天）

刚注册完的账号，当天**只做"落地确认"**：

- [x] 用注册时的 IP 与设备完成一次正常登录（web 端）
- [x] 阅读微软欢迎邮件（`Welcome to Outlook` / 微软服务协议邮件）
- [x] 打开「设置 → 个人资料」，确认姓名、生日信息完整
- [x] **不要**当天就发送任何邮件
- [x] **不要**当天就绑定任何高价值服务（广告账户、ChatGPT 等）

> 若注册时跳过/绑定了辅助邮箱或手机号，确认这些密保信息有效（这决定以后能否自助解封）。

### 阶段 1：适应期（第 1–5 天，关键期）

每天用**同一 IP + 同一环境**登录 1 次，执行少量真人行为：

| 天数 | 操作 |
|---|---|
| Day 1 | 登录 → 读欢迎邮件 → 浏览收件箱 → 退出（不要发信） |
| Day 2 | 登录 → 给自己另一邮箱发 1 封测试信 → 打开收到的信 |
| Day 3 | 登录 → 订阅 1–2 个新闻简报（Microsoft 官方或知名站点的 subscription） |
| Day 4 | 登录 → 与信任邮箱互发 2–3 封（每封内容不同） |
| Day 5 | 登录 → 整理邮件（建文件夹、打标签）、添加 1–2 个联系人 |

**本阶段禁止**：
- 群发邮件、批量注册第三方平台
- 多个账号之间互相大量互发（形成可疑环）
- 换 IP / 换设备 / 挂 VPN 换区

### 阶段 2：稳定期（第 6–14 天）

- 保持每天 1 次登录习惯（可改为隔天）
- 可开始**低频小规模**真实使用：少量平台注册、少量接码
- 单账号每天发送量建议 **≤ 10 封**，且内容差异化
- 继续保持同一 IP（静态住宅 IP 最佳，其次固定数据中心 IP）

### 阶段 3：成熟期（第 15 天后）

- 账号已积累一定信任分，可承载正常业务负载
- 仍建议：发送量缓慢递增（例如每周 +20%），不要突变
- 接码类账号：用于收信是最安全的用法，不发送不违规，存活率高

## 四、每日/每周养号操作清单

### 每日（3–5 分钟/账号）

```
1. 固定 IP 登录 outlook.live.com（或通过 Graph API 静默拉取一次收件箱）
2. 扫描收件箱，打开/阅读 1–2 封邮件（可用 IMAP/Graph 标记已读）
3. 清空垃圾邮件文件夹（spam 里如有正常邮件，移回收件箱——正向信号）
4. 退出登录（web 端）
```

### 每周

```
1. 用 Graph API 拉取一次完整收件箱 + 写一条草稿（模拟真人操作）
2. 检查账号状态：能否正常登录、有无安全警告（account security page）
3. 刷新 token（若使用 OAuth2 refresh_token 接码，确保 token 有效）
4. 清理异常的登录地点（若出现陌生国家登录，立即改密 + 移除设备）
```

### 自动化建议

- 用 **OutlookManage / outlook-helper** 类工具批量管理账号健康状态（token 有效性、错误码分类）
- 用 cron 定时执行 Graph API 静默登录（`GET /me/messages?$top=5`）实现"保活登录"，无需开浏览器
- 禁止：多个账号在同一秒发起相同请求（打散时间 + 随机间隔）

## 五、防关联（多账号必读）

微软会通过以下信号把多个账号关联到同一人，一旦关联，封禁呈"连锁反应"：

| 关联信号 | 隔离手段 |
|---|---|
| 相同浏览器指纹（Canvas/WebGL/GPU/字体） | 指纹浏览器（Hidemyacc/Octo/云登等）每账号独立指纹 |
| 相同 IP / IP 段 | 每账号独立代理（静态住宅 IP 最佳）；避免同一 IP 注册 >3 个/24h |
| 相同密码 / 辅助邮箱 / 手机号 | 每账号独立强密码 + 独立密保 |
| 相同行为模式（同操作、同时点） | 操作时间随机化、内容差异化 |
| 相同注册信息（姓名/生日） | 随机生成拟真资料（生日>18 岁，名字无规律） |

**规模参考**（社区经验）：
- <5 个账号：普通浏览器多 profile 可勉强
- 5–15 个：建议指纹浏览器 + 固定 IP
- >15 个：必须指纹浏览器 + 每号独立静态住宅 IP

## 六、异常处理

### 遇到"让我们来保护你的帐户"（保护页）

```
原因：注册 IP 信誉低，或触发了风险模型
处理：
1. 立即停止该账号的自动化操作
2. 用同一 IP 手动登录，走页面验证（邮箱验证码 / 手机验证码）
3. 若要求绑定辅助邮箱：绑定后该账号获得"恢复通道"，大幅降低永久封禁风险
4. 验证通过后，当天不再做任何其他操作，次日恢复低频养号
```

### 登录提示"检测到异常活动" / 临时封禁

```
处理：
1. 停止一切自动化，不要反复重试登录（会加重风控）
2. 通过 account.live.com 走验证流程（密保邮箱/手机号/联系客服）
3. 验证恢复后，换更干净的 IP，且前 3 天只做被动操作（只读邮件）
```

### Token 失效 / 密码错误

```
1. 检查 refresh_token 是否过期（MS refresh_token 长期有效，但若账号被风控会失效）
2. 用 Outlook-Oauth-GetToken / Device Code Flow 重新获取 refresh_token
3. 若密码失效：检查账号是否被强制重置（说明触发了安全事件）
```

> ```
> email----password----client_id----refresh_token
> ```

## 八、红线清单（绝对禁止）

- [ ] 同一 IP 一天内注册超过 3 个 Outlook 账号
- [ ] 新号当天群发 / 批量注册平台 / 绑定广告账户
- [ ] 多个账号共用密码、辅助邮箱、手机号
- [ ] 同一账号频繁跳区（美国 ↔ 香港 ↔ 新加坡来回）
- [ ] 用数据中心 IP（Azure/AWS/阿里云 裸 IP）注册（信誉极差）
- [ ] 多个账号在完全相同的秒级时间点做相同操作
- [ ] 忽略微软安全预警 / 反复重试被封的账号
- [ ] 用第三方软件（非官方页面）做 OAuth 授权（易触发异常）

## 九、FAQ

**Q1：接码号（只收信）也需要养吗？**
需要，但成本低。收信是最"安全"的用法，只要保证：固定 IP 登录、token 有效、不发送邮件。可通过 Graph API 每日静默拉取实现低成本保活。

**Q2：token 号（买来的带 refresh_token）怎么养？**
先验证 token 有效性（Graph API 调 `GET /me`），再纳入每日保活队列。注意：token 号通常无密码登录能力，养号全靠 API 层操作，勿尝试网页登录（会触发验证）。

**Q3：养多久才能跑量？**
保守 2 周（适应期 5 天 + 稳定期 10 天）。Gmail/Outlook 社区普遍经验：14 天后风险大幅下降，30 天为"完全成熟"。

**Q4：被封了还能救吗？**
临时封禁可通过密保验证恢复（前提：绑定了辅助邮箱/手机号）。永久封禁基本不可逆。**所以注册时绑定辅助邮箱是性价比最高的保险。**

**Q5：脚本登录会触发风控吗？**
低频 + 拟真 + 打散时间的前提下，Graph API / IMAP 协议登录风险可控（许多开源工具就这么干）。高频、集中、无随机间隔的脚本登录才是触发源。
